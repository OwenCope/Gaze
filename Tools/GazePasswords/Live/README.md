# Gaze Passwords — local vault / browser integration candidate

This is a separate app from the sample-data design preview. It has a macOS-authenticated
local Keychain vault, add/edit/delete/favorite/reveal/copy UI, a signed native browser
host, and an opt-in Gaze face-approval service. It is **not yet verified end-to-end or
ready to ship**. Keep test credentials synthetic until the acceptance checklist passes.

## Opt-in setup

Do not install an extension or modify the browser profile without the owner’s approval.
Both apps must have the same trusted Apple signing team. An ad-hoc signature fails closed.

**Current runtime policy (September 14):** following the earlier password-replay hold,
the owner explicitly requested automatic unlocking again. The rebuilt Gaze app requires
a fresh saved opt-in as well as the keystroke backend and all recognition/session gates.
The owner-authorized opt-in was enabled and the normal app relaunched at 16:12 local time;
walk-away locking remains off. Scan-only mode still cannot deliver passwords. The earlier
rejected-input reports have not been explained or verified fixed by a real unlock test.
Browser setup is not permission to change Mac unlocking or to enter credentials. Live
browser/face verification remains a separate, owner-supervised acceptance step.

1. Launch the new Gaze Passwords app. Unlock through macOS and add a **synthetic** login
   with an exact HTTPS origin. The app stores nothing until Save is pressed.
2. Run the updated normal Gaze build and use Check Gaze connection in Passwords Settings.
   Normal Gaze serves browser approvals only while the owner session is unlocked.
   Explicit `--browser-only` mode also works. `--scan-only` supports browser approvals in
   the unlocked owner session alongside lock/wake scanning, without password replay or
   automatic locking. UI-review mode cannot approve browser requests. Do not run multiple
   Gaze instances or change modes mid-request.
3. In Passwords Settings, choose the detected browser and **Connect browser…**, then
   confirm registration. This creates one native-messaging manifest, not an extension.
   It refuses conflicting files. The manual `script/install-browser-helper.mjs --install`
   tool remains available for its supported fixed installation paths.
4. In that browser’s Extensions page, enable developer mode and load
   `build/browser-integration/browser-extension`. Verify the ID against
   `Gaze Passwords.app/Contents/Resources/BrowserIdentity.json`.
5. On a supported synthetic HTTPS login form, click the extension’s key, choose Fill,
   unlock Passwords, and approve an exact-site login. Gaze is located and launched when
   needed, but an already running old/UI-review copy must be restarted by the owner.
6. Follow both movements. A matching identity, continuous fresh frames, two challenges,
   configured strong embedder and mandatory existing anti-spoof gate are required.
   Passwords fills only after approval. **It never submits the form.**

## Boundaries

- The vault is separate from Gaze’s account-password store; no migration or access to that
  password. macOS user-presence authentication protects the Data Protection Keychain item.
  Face verification does **not** satisfy or replace the Keychain authentication ACL.
- Vault mutations update one archive. Revision checks reject conflicting writers. Failed
  reads/writes never delete or recreate the vault. No real credential was used in development tests.
- The current app is not sandboxed because the prototype transport uses private Unix
  sockets. Hardened Runtime, same-team identifiers and audit-token peer validation apply.
  Shipping still needs entitlements/provisioning review, notarization and independent review.
- Unlock material lasts at most five minutes and is discarded on app departure, close,
  sleep or session lock. Swift strings cannot promise guaranteed memory zeroization.
- Copies use concealed/transient pasteboard markers and are cleared on lock or after
  30 seconds only if no other app has replaced the clipboard. These markers are advisory;
  clipboard managers might ignore them. Browser filling never uses the clipboard.
- Only exact HTTPS origins. No suffix/domain guessing, HTTP, cross-origin frames, GET
  forms, registration/change-password forms, multiple visible password fields, or form
  action overrides. Unsupported forms fail rather than guessing. No auto-save/harvesting.
- Permissions are `activeTab`, `scripting`, `nativeMessaging`; no all-sites permission,
  remote code, web-accessible resources, external message handler or cloud vault.
- A document ID, nonce, monotonic deadline, original field references, unchanged field
  values and current form origin bind filling. Navigation/disconnection cancels the request.
- Websites can read a password after it is placed in their login form. No password manager
  can make an already compromised relying-party website trustworthy.
- Native host stdout is only length-framed protocol JSON. No credentials are logged.
- The unpacked extension key stabilizes its ID; it is not cryptographic publisher proof.
  Native approval and signed app peers remain required. Store-signed distribution remains work.
- Safari, native app autofill, sync, recovery, passkeys and face-only vault unlocking
  are **not implemented** in this candidate.
- Experimental spoof models are unchanged. This work does not establish spoof resistance.

They test protocol/model/form boundaries, not a browser installation, Keychain persistence,
real recognition performance or a live lock-screen unlock.

## Password-replay containment

Following another report of rejected lock-screen input, the older running Gaze process was
stopped. Gaze's `unlockBackend` was set to `none` and `walkAwayLock` to false; stored passwords,
face enrollment, installed authentication components and other apps were not modified.
That initial containment was **not a verified fix for rejected password delivery**.
The owner subsequently requested re-enabling automatic unlocking. `PasswordReplaySafety`
now requires a fresh persisted opt-in before password reads, including callers that bypass
the readiness UI. A prior backend preference alone does not restore automatic unlocking.
Normal launch starts lock observation only with that consent and the keystroke backend.
Do not enable it during browser testing without the owner's separate request.

Browser requests additionally bind an `AutofillSessionLease` before bringing up the vault;
lock, sleep or session changes cancel the request and discard its vault session. Release
requires that same console session to remain unlocked. No macOS account-password typing is
part of this browser path.

The vault unlock flow now allows a bounded two-second foreground handoff after successful
macOS authentication, without reading or revealing the vault while inactive. Generation,
cancellation and final activity checks still apply. Authentication cancellation is quiet;
interruption has its own explanation rather than a misleading password-edit alert.
Run `bash Tools/GazePasswords/test-unlock.sh` for mock-authentication lifecycle regressions.

## Pasting website addresses

The password editor accepts a complete HTTPS login URL and previews its exact matching
origin before saving. Paths, queries and fragments are omitted from the saved record;
subdomains and non-default ports remain distinct. Use the address of the actual login
page, not a site's parent domain. URLs containing credentials or invalid hosts are rejected.
This editor-only normalization does not relax `BrowserOrigin` validation for browser IPC.
`test-browser.sh` checks normalization, archive round trips and cross-origin rejection
using synthetic in-memory data, without reading or writing the Keychain.

## Settings and CSV import — September 14, 2026

The live target now includes native Settings (Command-comma), a toolbar Settings button,
and Import entry points in File, the toolbar, the empty vault and the menu-bar menu.
Settings and the locked vault reuse the previous preview's actual companion renderer,
appearance modifier and glass background. The floating Apple export guide is shared too;
the sample-data vault and simulated approval are not linked into the live target.

CSV import accepts UTF-8 Apple Passwords, Bitwarden login exports, and URL/Username/Password
column exports, up to 2 MB and 1,000 rows. The owner chooses a file; review shows counts,
not credentials. Only exact HTTPS origins are imported. Unsupported/invalid rows and
nonempty extra fields are disclosed. Notes, passkeys and custom fields are
not imported. Malformed CSV rejects the whole file. Existing passwords are never
overwritten: matching records are skipped and conflicting passwords are counted separately.

Confirming imports writes one revision-checked Keychain archive. A failed write leaves
the in-memory vault unchanged. Lock/session changes discard the review and invalidate
pending file choices; ordinary app departure also locks from the import window. The guide
may remain during normal app switching, but never reads the screen or credentials.
The source CSV is not uploaded, copied, deleted or remembered by the app. The owner must
verify the result and remove the plaintext export when no longer needed.

Run `test-import.sh`, `test-unlock.sh`, and `test-live-layout.sh` in this directory for
synthetic parsing/lifecycle checks and offscreen Settings/Import renders. No real CSV,
Keychain persistence, automatic browser capture or face-only vault unlock was tested.
Automatic browser saving and face-only vault unlock remain unimplemented. In particular,
Gaze verification does not satisfy the existing macOS `.userPresence` Keychain ACL.

The restored Settings toolbar button, Settings-to-Import action, and floating export
guide were also opened and checked in the storage-disabled UI review build. Rounded
glass controls and the shared companion rendered in that window. The review app was
then quit; the owner's running vault/editor was not restarted or inspected.

## Verification codes and approval handoff — September 14, 2026

TOTP setup keys can now be added to entries and imported from Apple `OTPAuth` or Bitwarden
`login_totp` columns. The detail view shows a current code, countdown and copy action that
expires at the end of that code's period (or on locking/app departure). Setup keys are
excluded from search and kept inside the same user-presence-protected archive. Editing
an unrelated field preserves the key without displaying it. Unsupported OTP data causes
the entire import row to be skipped, with an explicit count, rather than silently losing
the second factor. Reimporting an entry with a different key is a conflict, not a duplicate.

Archives with OTP data use version 2; existing version-1 archives remain readable.
Older app builds reject version 2 rather than discarding codes. Do not downgrade after
saving codes. No existing vault was read or migrated during development. TOTP tests cover
RFC 6238 vectors, parsing, invalid parameters, archive round trips and import behavior.
Passkeys require a real credential-provider registration/assertion implementation and
are not represented as arbitrary strings or claimed as imported from password CSVs.

Normal Gaze starts its signed browser-approval listener independently of Mac unlocking.
Scan-only mode also serves browser requests, but only in the unlocked
owner session; UI-review mode cannot serve them. This does not enable password delivery.
Face enrollment/test capture windows, pause, lock/session changes, failed anti-spoofing,
stale evidence and lockout still block verification. Locking immediately invalidates the
browser session and stops its camera/panel before any browser approval can be returned.
The status operation only reports readiness and never returns an approval, face data or
credentials. Passwords Settings has an explicit connection check; startup waits up to
15 seconds within the original request lease for Gaze to finish loading its model.
Passwords first connects to an already-running, signature-verified Gaze service. It launches
Gaze only when the socket is unavailable; a signature/trust failure does not trigger another
launch or a weaker fallback. Lock, focus loss, cancellation and vault revision changes
during startup stop the request before camera verification begins.

`test-gaze-status.sh` uses a temporary same-team signed client with the Passwords identifier
to query readiness only. The handshake succeeded against the relaunched normal Gaze build;
no camera was started. This is not end-to-end browser verification and does not bypass the
vault's macOS authentication or establish that Mac password delivery works.

The September 14 integration follow-up confirmed signed status handshakes with the running
scan-only Gaze app and Passwords app separately. `test-passwords-status.sh` uses a temporary
same-team client carrying the native helper identifier, and `test-gaze-status.sh` uses the
Passwords identifier. Both send only `status`, are bounded to five seconds after connecting,
and neither starts a camera nor reads or unlocks a vault. These are endpoint checks, not an
installed-extension or successful face-approval test.

## Browser save, setup and vault polish — September 14, 2026

The extension now has **explicit Save this login**, not background password capture.
It reads one eligible same-origin HTTPS POST login form only after the owner clicks Save,
then asks for confirmation inside the unlocked Passwords app. No form is submitted.
An exact website-and-username match updates the existing password while preserving its
title, collection, favorite and verification code. Ambiguous duplicates are rejected.
An unchanged password requires confirmation but does not rewrite the archive. Approval is
bound to the original vault session, archive revision, console session and request lifetime.
Lock, navigation, disconnect, cancellation or a revision change invalidates the request.
The native acknowledgement never contains credentials.
After a successful save or confirmed unchanged login, Passwords reveals that entry instead
of leaving it hidden behind a previous search or Codes/collection filter. Browser fill
requests use compact username/collection choices, with search scoped to the exact website
when several accounts match. Other-site results are never offered by that chooser.

The native host validates each response against the original operation and exact request
identity before forwarding it: only approved `filled` replies may contain bounded username
and password fields; status, save acknowledgements and errors cannot contain credentials.
It now checks an unlocked-owner session before connecting or launching Passwords. Existing
authenticated sockets are reused rather than activating the app for every status check.
Lock/sleep/session changes close pending exchanges, and the session is checked again before
output. The native browser-parent signature and exact extension origin are still required.

`test-native-session.sh` covers these lifecycle gates with fake sessions and anonymous socket
pairs. `test-browser-fill.sh` exercises the real Passwords fill handler with an in-memory
vault and a fake Gaze socket: explicit choice, existing/cold startup, malformed replies,
changed vaults, session changes, focus loss, lock and cancellation. Neither grants face
approval in production or accesses real credentials.

Settings can open the selected, signature-verified browser's Extensions page directly.
This does not install an extension. Helper contact is labeled separately from the listener
state; only Check app connection inside the installed extension verifies the browser path.
Cancelled native requests are checked before launching, during connection retries and
before forwarding a response. Closing the browser pipe shuts down an attached socket.
Incoming/outgoing frames are bounded before decoding/writing. Browser and companion
signature checks remain required; none were replaced by a test bypass.

The extension repeats response-shape and UTF-8 size checks before page injection. Malformed
replies produce normal failure messages rather than JavaScript type errors. It drops
references to received username/password fields on success, rejection and page-injection
failure. This limits retention; it does not promise zeroization of JavaScript strings.

Reopening the popup restores pending/saved/filled status from service-worker memory;
this state contains no credentials, expires after 90 seconds and clears on navigation.
The extension's information disclosure includes a connection-only check, which opens
the app but does not unlock the vault, inspect the page or request camera approval.

Settings now includes **Connect browser…** with a confirmation dialog. It verifies the
app, helper and selected browser signatures, then writes a user-only native-host manifest.
Browser discovery uses Launch Services plus system/user Applications folders, so a signed
browser can be moved or renamed without being tied to one filename. Candidates must match
the browser's exact bundle identifier and publisher; an impostor with the right filename
does not appear. Verification runs off the UI thread and is cached for the Settings view;
the refresh button checks again. Registration independently rechecks the selected app's
signature, so discovery is not an authorization token.
Directory traversal is descriptor-relative and refuses symlinks or writable-by-others
directories; conflicting existing registrations are never overwritten. This registers
the helper only. The owner still loads the bundled `BrowserExtension` directory on their
browser's Extensions page. **Show extension** reveals that exact bundled directory.
The button is disabled when the bundle has no extension directory. Multiple detected
browsers use visible capsule choices instead of a dropdown; a single browser is shown
directly. Setup has a busy state and short result text, with details in its information
popover. Theme selection also uses the shared Gaze glass capsule buttons.
No browser profile or extension was installed during development of this change.

The editor uses Gaze's existing companion, capsule glass fields and system glass buttons.
Verification codes have a separate add/edit flow with a login chooser and live code preview.
Existing setup keys are never prepopulated, and replacement/removal require confirmation.
The Codes detail shows the code and username, with a link back to the password rather than
duplicating password controls. Longer matching/import/setup explanations live in the shared
information popover rather than permanent paragraphs. A generator uses
`SecRandomCopyBytes` and rejection sampling to create 24-character passwords, without
copying or saving automatically. Replacing existing editor text requires confirmation.
Personal/Work collection selection, username copying, copy feedback, selection-scoped
password hiding and session-bound delete confirmation are included. Command-F focuses
search and Command-N creates a password or code in the current section; both commands are
disabled while locked or editing. Personal/Work selection uses shared glass capsule buttons.
Search has a clear control and keeps selection on a visible result. Saving an edited login
reveals it even when its new collection no longer matches the previous filter. Favorites
and empty collections explain their next action. Verification-code editors disable saving
invalid setup keys and use the same multiword search as the vault. Successful imports select
the first new login and offer a return to the vault.
Stale password, favorite and verification-code edits cannot overwrite newer archive entries.
Deleting a login now requires a confirmation bound to its identifier, the current unlock
session and the archive revision. A browser update, import, favorite change or any other
archive mutation invalidates an older confirmation. Lock/reunlock also invalidates it,
even when the persisted archive is unchanged. Missing entries and repeated confirmations
do not produce empty writes. Failed persistence preserves both the login and selection.
The dialog names the login and explicitly warns when its saved verification code will
also be removed; it does not claim to delete the website account. Confirmation state
contains identifiers and display metadata, not the password or setup key.

Security review is entirely local: it identifies exact reuse and passwords shorter than
12 characters. It is not a breach check, entropy score or safety guarantee. The review
filter respects search, and all derived state disappears on lock. Generating or editing a
password here never changes the password on a website.

Website icons are **opt-in and disabled by default**. They request only `/favicon.ico` on
the exact HTTPS origin, without cookies, stored credentials, redirects or a third-party
favicon service. Google Accounts has one explicit fallback to `https://www.google.com/favicon.ico`
when its own icon fails; parent domains and redirect destinations are never inferred.
The fallback uses the same pinned transport and image validation. DNS is resolved once per
host; any private, local, documentation or otherwise
disallowed address rejects the answer set. The connection uses a validated numeric
`NWEndpoint.Host` directly, with the original hostname retained for SNI and default TLS
certificate validation. There is no second hostname lookup at connection time. Proxy
connections are rejected before the HTTP request is sent. Only HTTP/1.x status 200 and
PNG, JPEG or ICO MIME types are accepted; redirects and compressed responses are rejected.
The bounded parser rejects ambiguous framing, truncated bodies and malformed chunks.
Downloads are bounded to four concurrent requests, 256 KiB, 32 frames and 4096px per side;
each connection has an eight-second deadline. Thumbnails are 96px and remain in memory only.
Locking cancels active requests and discards the cache. Cancelled rows cannot exhaust the
request slots or repopulate a cache cleared on lock. Initials are the offline fallback.
Settings offers a reload control when icons are enabled and the vault is unlocked. Cache
generation changes restart visible icon tasks, so retrying does not require relocking.
The site still observes the connection and IP address; DNS and network routing remain
OS-managed. Downloads remain off by default, and no saved-site requests were used in testing.

### Verification and remaining release gates

The extension popup offers Cancel request while approval is pending. Only the extension's
own popup can request cancellation; it disconnects the active tab's native request and
invalidates its document-bound operation. Cancellation does not undo a save or fill that
already completed. A late completion cannot overwrite cancellation feedback. These paths
are covered using mocked browser APIs, not an installed extension.

`test-navigation.sh` exercises search, collection changes, saved-login visibility, removing
codes/favorites from their filtered views, persistence failures and lock boundaries using
in-memory fixtures. It is included in the offline regression suite.

Run `bash Tools/GazePasswords/test-offline.sh` for the explicit offline regression set.
It includes the synthetic lock-screen submission/production-hold tests but never posts
keyboard events. It deliberately excludes live TLS fixtures, Gaze status probes, app
launches and browser/profile installation. Passing this command does not prove production
Keychain persistence, live face approval or end-to-end browser filling.

- `test-browser.sh`: protocol/origin/archive/save-proposal/generator/review tests, plus
  JavaScript form and worker tests (including navigation and popup-result restoration).
- `test-browser-save.sh`: actual asynchronous save-service behavior against injected,
  in-memory archives, including locked approval, cancellation, revision changes and
  console-session invalidation. Anonymous pipes and Unix socket pairs also exercise
  native framing → socket transport → save service → secret-free acknowledgement for
  new, updated and unchanged logins. No real browser or camera participates.
- `test-native-bridge.sh`: fragmented/truncated pipe frames, malformed requests, bounded
  responses, operation-specific secret restrictions and cancellation of socket reads.
  These fixtures do not exercise signed browser-parent or companion-peer acceptance;
  those remain part of the supervised browser test.
- `test-removal.sh`: revision/session-bound deletion, missing entries, failed persistence,
  linked-code removal and replay rejection using only synthetic in-memory archives.
- `test-browser-setup.sh`: temporary-directory fixtures covering atomic creation,
  idempotency, conflicts, symlinks, traversal and permissions; discovery fixtures cover
  moved/renamed apps, impostors, deduplication and fallback selection. No real profile is changed.
- `test-icons.sh`, `test-unlock.sh`, `test-import.sh`, `test-verification-code.sh`:
  bounded icon policy/parser/cache (including fragmented responses and cancellation),
  authentication lifecycle, import and public TOTP vectors. These tests do not contact sites.
- `test-icons-network.sh`: opt-in live network test using only fixed public fixtures:
  a Google favicon and BadSSL hostname/expired/self-signed certificate failures. Confirms
  direct pinned-IP transport can download an image while default TLS validation rejects
  invalid certificates. It never reads vault entries or uses saved websites.
- `test-live-layout.sh`: light/dark rendering with synthetic archives. Offscreen renders
  do not faithfully capture system glass or Metal; native UI inspection is also required.
- `script/build-interaction-review.sh`: a separately identified, ad-hoc-signed test app
  with only synthetic, in-memory archives and no browser listener. It does not ship in
  the live bundle. Add/generate/save, cancel/reopen, the security-review filter, the actual
  glass editor and light/dark Settings were exercised there. This is **not** proof of
  production Keychain persistence or live browser authentication.

The live app and extension build successfully, but end-to-end browser installation,
Keychain-backed save/fill and live face approval still need an owner-supervised test.
Face-only vault unlocking, background automatic capture, Safari and passkeys remain
unimplemented. The installed SDK supports macOS passkey credential-provider APIs, but
this project has no signed provider-extension target or provisioned provider entitlement;
the current profile authorizes the application and Keychain group only. Do not market
password CSV import as passkey import or weaken the vault ACL to simulate Gaze-only unlock.

Mac account-password replay requires the owner's separate explicit opt-in. These Passwords
features do not fix or verify the earlier incorrect-password behavior on the macOS lock
screen. Synthetic tests and compilation do not establish successful password delivery.
